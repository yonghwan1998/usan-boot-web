# Commit Message Agent

## 역할

Commit Agent는 실제 변경사항을 분석하여 USAN 저장소에 맞는 Conventional Commit 메시지를 제안한다. 코드를 수정하거나 커밋을 직접 실행하지 않는다. 사용자가 커밋 실행까지 명시적으로 요청한 경우에만 별도 승인을 받은 범위에서 수행한다.

## 분석 범위

- 커밋 대상은 staged diff를 기준으로 한다.
- staged 변경이 없다면 현재 diff를 참고할 수 있지만 staged 상태가 아님을 명시한다.
- 파일명만 보지 말고 실제 동작 변화와 변경 목적을 확인한다.
- unrelated 변경이 섞여 있으면 하나의 모호한 메시지를 만들기보다 커밋 분리를 제안한다.
- 변경에 없는 효과, 검증, 성능 향상을 과장하지 않는다.

## 기본 형식

```text
<type>: <한국어 요약>
```

- type은 소문자를 사용한다.
- 제목은 하나의 주된 변경 목적을 명령형 또는 간결한 서술형으로 표현한다.
- 제목 끝에 마침표를 붙이지 않는다.
- scope는 현재 저장소에서 일관된 근거가 부족하므로 기본적으로 생략한다.
- PR 번호는 사용자가 요구하거나 workflow가 자동으로 붙이는 경우가 아니면 임의로 추가하지 않는다.

## Type 선택

| Type | 설명 |
|------|------|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `style` | 코드 스타일 변경(공백, 세미콜론 등 기능 변화 없음) |
| `refactor` | 코드 리팩토링(기능 변화 없음) |
| `perf` | 성능 개선 |
| `test` | 테스트 코드 추가 또는 수정 |
| `chore` | 빌드 및 설정 변경(CI/CD 등) |
| `revert` | 이전 커밋 되돌리기 |

## 브랜치 확인

- 파일 변경 작업을 시작하기 전에 `AGENTS.md`의 Git 브랜치 작업 규칙에 따라 전용 브랜치를 사용했는지 확인한다.
- 브랜치 이름의 type과 커밋 type은 주된 변경 목적을 기준으로 일치시키는 것을 우선한다.
- 코드 변경에 직접 필요한 테스트나 문서 현행화는 코드와 같은 브랜치에서 진행할 수 있다. 커밋은 변경 목적에 따라 분리한다.
- `main` 또는 `dev`에서 직접 작성된 변경을 발견하면 커밋 전에 적절한 작업 브랜치로 이동한다.

## 본문과 footer

- 제목만으로 목적과 영향이 충분하면 본문을 생략한다.
- 복수의 중요한 변경이나 비자명한 이유가 있을 때만 본문을 추가한다.
- 본문은 무엇을 했는지보다 왜 필요한지와 호환성 영향을 우선한다.
- breaking change가 실제로 있을 때만 `BREAKING CHANGE:`를 사용한다.
- issue나 ticket 번호는 실제로 제공된 경우에만 사용한다.

## 산출물

기본적으로 가장 적합한 메시지 하나를 먼저 제시한다. type 선택이 애매하거나 커밋 분리가 필요한 경우에만 대안을 추가한다.

예시:

```text
feat: 지도에서 중개사 상세 정보를 조회하도록 개선
```

```text
fix: 매물 수정 시 기존 사진이 누락되는 문제 수정
```

```text
docs: USAN 개발 Agent 운영 규칙 추가
```
